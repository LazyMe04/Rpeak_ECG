# G14 — Vietnamese UI

Status: **complete**. The app ships in Vietnamese; English is the option. Every
page is translated — the monitor, both worker toggles, the AI Model card and the
Docs guide — and no number is left in the other language's convention.

The interesting part of this milestone is not that a dictionary exists. It is
that the first complete-looking pass left ten section headings and every contents
entry on the model card in English, while the audit reported 100% coverage and
the page looked finished in a screenshot. The reason is structural, and it is
written down below because the same shape will recur.

## The English sentence is the key

`t("Heart rate")` returns `"Nhịp tim"` in Vietnamese and `"Heart rate"` in
English. There is no `en` dictionary, no key namespace, and no build step.

The trade is deliberate. A key-path design (`panel.hrv.title`) needs a second
dictionary even for the language you wrote the app in, and a missing entry shows
`.title` on the screen. With the sentence as the key, a missing entry shows the
English sentence — degraded, but readable and correct. Vietnamese reordering is
handled by reordering the translation, and `{name}` interpolation covers the rest
(`t("Patient {id}", { id })`).

Vietnamese has no plural forms, so `{n} beats` reads the same at 1 and at 12 and
no plural machinery was written.

Resolution order is `?lang=` → `localStorage["rpeak.lang"]` → `vi`, so a link, a
screenshot or a smoke run can pin the language without disturbing a reader's
stored choice. `document.documentElement.lang` follows it, which is what makes a
Vietnamese page read as Vietnamese to a screen reader.

## Numbers are not text

`72.7%` in English is `72,7%` in Vietnamese, and `7,156` is `7.156`. A page that
translates its prose and leaves `toFixed()` in place is the single most common
way a Vietnamese UI looks unfinished: the words are right and the numbers are
foreign.

So every displayed number goes through `num(v, digits)`, which calls
`toLocaleString("vi-VN")` or `"en-US"`. The awkward cases were formatters defined
at module scope (`pct`, `fmt`, `num`) — a module-level helper cannot see the
locale context, so each was moved inside its component and closed over the hook:

```tsx
const { t, num } = useT();
const pct = (v: number, d = 1) => `${num(v * 100, d)}%`;
```

The one place that keeps dot decimals is the CSV export in
`src/lib/ecg/report.ts`. It is a comma-separated file: a Vietnamese decimal comma
would split one value into two fields and corrupt every downstream reader. The
comment sits next to the `toFixed` that keeps it that way.

`smoke-lang` asserts this directly rather than by reading source — it derives the
model's held-out accuracy from `beatcnn.eval.json`, then requires the page to
print `72,7%` in Vietnamese and `72.7%` in English, and to _not_ print the
dot-decimal form anywhere in Vietnamese prose.

## Diagnostics: our sentence, someone else's detail

The worker hooks report failures as `"<our sentence> — <exception text>"`:

```
no model at data/models/beatcnn.json — Failed to fetch
```

Only the left half is ours to translate; the right half is whatever the runtime
threw and translating it would be a lie. `td()` splits on the em dash the hooks
join with, translates the head, and leaves the rest as it arrived:

```ts
export function translateDetail(lang: Lang, message: string): string {
  const i = message.indexOf(" — ");
  if (i < 0) return translate(lang, message);
  return `${translate(lang, message.slice(0, i))} — ${message.slice(i + 3)}`;
}
```

Three unit checks pin it: the split case, a message with no detail, and an
unknown sentence (a raw JSON parse error) that must pass through unchanged in
both languages.

This also taught the audit something. `check_i18n.py` found the key
`no model at data/models/beatcnn.json` unused, because it exists only as the
static head of a template literal and never appears inside a `t(` call. The audit
now reads template literals, cuts them at the first `${`, and strips the trailing
dash — the same split `td()` performs.

## The blind spot: props on components that translate themselves

The audit reads `t("...")` calls. `smoke-pages` reads English labels. Both passed
while the model card's ten section headings and every contents entry rendered in
English, because of how the pages are built:

```tsx
<Section title="Training"> … </Section>   // Section renders t(title)
<PageShell sections={[{ id, title: "Parity" }]} />  // renders t(s.title)
<KV k="Optimiser" v={…} />                // renders t(k)
```

No `t("...")` call anywhere in the page names `"Training"`. The string is an
_attribute_; the translation happens one component deeper. A grep for `t(` cannot
see it, and neither could any smarter regex: the string is not missing from the
dictionary — it is missing from the dictionary _and_ from the set of things the
audit knows to look for.

This was found by rendering the page in Vietnamese, reading the screenshot, and
then diffing the rendered VI and EN text of the same page. The fix was to key the
strings, not to extend the regex: `Section` and `PageShell` already translate, so
the page only needed correct entries, and the architecture table's row labels had
to move from render-time `t(r.op)` to construction-time `t(...)` inside the memo
(with `t` added to its dependency list, or the table would not follow a language
switch).

The durable answer is `smoke-lang.ts`, which requires the rendered page to have
at least ten contents entries and ten section headings, then fails if any of them
is one of the known English titles. Without the count check the assertion would
pass on an empty list — a page whose sections failed to render looks exactly like
a page with no leftovers.

A diacritic heuristic was tried here and removed: "Tachogram R-R", "{i}/{n}" and
"qua middleware Vite" are correct Vietnamese with no diacritic, and a check that
cried wolf 41 times is a check nobody reads.

## The same blind spot through a variable

G15 turned up the second shape of the same problem. The catalogue stores
`ok` / `saturated` / `low-amplitude` / `flat` / `implausible-hr`, and the vitals
panel rendered `segment.quality` straight into the page. Once the dictionary had
`"saturated": "Bão hoà"`, the audit was satisfied — the entry existed and the
literal appeared somewhere in the source. But nothing named it at the render
site, and a reader on a saturated segment saw the ASCII machine value.

```tsx
<span>{segment?.quality}</span>                 // before: "saturated"
<span>{t(qualityLabel(segment?.quality))}</span> // after
```

`lib/quality.ts` now owns the mapping (and the colour, `qualityTone`), because
two render sites — the vitals panel and the segment picker — had each formatted
it locally and drifted. The audit cannot prove a variable-driven string is
translated; only rendering it can. `smoke:lang` loads `p00003_s00` (saturated),
opens the vitals panel, requires `Bão hoà`, and fails if the word `saturated`
appears anywhere in the body text.

The general lesson: the audit's guarantee is "every literal a `t(` call names
has an entry". It is not "every string on the screen went through `t`". Those
are different claims, and only a rendered diff tests the second.

## What is deliberately not translated

Some strings are identifiers, not prose, and translating them would make the app
lie about what it is showing:

`p00000_s00 · Icentia11k` (a record id and a dataset name), `npm run dev`,
`D:\Rpeak-Desktop\app` (a path), `?record=…&t=600` (a query), `Shift + ← →`,
`clip(0.5 × R-R, 50 ms, 150 ms)` (a formula), `Icentia11k (PhysioNet)`, `99 BPM`
(a unit). The VI-vs-EN render diff ends at one legitimate leftover per page, and
these are it.

## Verification

```
python -I pipeline/check_i18n.py   # 434/434 keys, 0 unused, 0 mismatched, 93 via a variable
npm run test:i18n                  # 15 checks
npx tsc --noEmit
npm run build
npm run smoke:lang                 # 29 checks: default, switch, persistence, ?lang=, numbers, headings, quality, title
npm run smoke:app                  # the packaged .exe, in Vietnamese first (10 checks)
```

The dictionary holds 527 entries; 434 of them are named directly by a `t("...")`
call and the other 93 reach the screen through a variable (`t(CLASS_MEANING[c])`,
`t(hrv.reason)`, `t(qualityLabel(seg.quality))`), so the audit counts them as
used only when the literal also appears somewhere in the source.

`smoke:lang` runs in its own Edge profile (`edge-smoke-lang`) because it stores a
language preference; sharing a profile with `smoke-pages` would let one suite's
stored `en` break the other's assertion about the default.

`smoke:app` is the one that runs against the shipped binary. It clears
`rpeak.lang`, reloads, and asserts the packaged build _starts_ in Vietnamese
before switching it to English — because every other assertion in that file looks
for an English label. Both halves matter: on a stale binary built before this
milestone, the switch was absent and the app was already English, so "pressing EN
switches the app to English" passed without anything having been switched. The
check now requires the page to have left Vietnamese, and the boot check requires
it to have been in Vietnamese to begin with.

The first attempt at that also exposed an operational trap worth recording: `npx
tauri build` without `PATH="$HOME/.cargo/bin:$PATH"` exited 0 while printing
`program not found`, because the wrapper's own `npm run build` step succeeded.
The exe on disk was two days old. The build log's exit code came from the last
command in the chain, not from the build. `docs/packaging.md` already says cargo
is off the PATH; the lesson is that a green exit line is not evidence a binary
was rebuilt — the timestamp is.

## What G15 added here

Five labels for the quality values, the error-boundary heading and body, a
translated noun for each boundary (`the model card`, `the guide`, `the monitor`,
…), `Try again` / `Reload`, and the missing-segment notice with its button. The
window title is composed from a translated page name, so `Hướng dẫn — Rpeak`
follows a switch to Vietnamese and `Docs — Rpeak` follows a switch back.

The boundary's `lang` is a **prop**, not `useT()`. A boundary renders above the
tree that threw; if the throw came from inside `LocaleProvider`, reading the
context there could throw a second time. `storedLang()` in `lib/i18n.tsx` is the
same fallback chain the provider uses (`?lang=` → localStorage → `vi`), exported
so the outermost boundary in `main.tsx` — which sits _outside_ the provider — can
still speak the reader's language.

The runtime's error text is deliberately not translated. It is a JavaScript
message, like the worker diagnostics `td()` leaves alone: our sentence is
translated, the runtime's is quoted.

## Not done

- **No third language.** The design accommodates one (`LANGS`, `Lang`), but only
  VI and EN exist and only those two have formatting tests.
- **No translation workflow.** The dictionary is a TypeScript file edited by
  hand. A second translator would want an export/import round trip and a review
  state per key; with two languages and one author that is machinery without a
  user.
- **The audit still cannot see prop-translated strings.** `smoke-lang` covers the
  pages it renders; a future component that translates an attribute and is never
  rendered in a smoke test would slip through exactly the way the model card
  headings did. The general fix — making `Section` take a key rather than a
  sentence, and typing it so an unkeyed string fails to compile — was not worth
  restructuring three components for, but it is the right answer if this recurs.
